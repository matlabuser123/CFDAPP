## 2. Architecture (minimum general-geometry architecture)

**Conformal multi-block structured quadrilaterals**, built into the existing face-based `Mesh`
(`cells`, `faces` with owner/neighbour, named `BoundaryPatch`es). No new solver data structure:
every solver, gradient, correction and exporter already works on arbitrary owner/neighbour
face lists, so a multi-block mesh is solved by the unchanged production solvers.

- `cfd::mesh::MultiBlockSpec` (new `include/cfd/mesh/MultiBlockSpec.hpp`): blocks (name, nx, ny,
  vertex grid — each a `structured_quad` grid), interfaces (two block sides, `aligned` /
  `reversed`), named patches (lists of whole block sides).
- `MeshGeometry::createMultiBlock2D`: cells block by block (local `j·nx + i`), faces per block
  in the single-block order; an interface side contributes its faces once (owner = `first`
  block's cell, neighbour = `second` block's cell), so an interface is ordinary internal
  faces — no interpolation, no duplicated one-sided faces, no flux mismatch by construction.
  Cell and face geometry use the same helpers (bit-identical arithmetic) as `structured_quad`
  ([logs/01](logs/01_quad_helper_refactor_bitcheck.log): 960 meshes bit-identical).
- `Mesh` keeps one `StructuredGrid` per block (named) for export; `structuredGrid()` is the
  single grid only when there is exactly one.
- Holes (regions no block covers) are internal solids; their edges are boundary patches.
- Explicitly **not** implemented (per the authorization): triangles, polygons, general
  unstructured adjacency, CAD import, Delaunay, remeshing, AMR, 3D, a mesh editor.

## 3. Production geometry format

`mesh.json` `"type": "multiblock"` with `blocks`, `interfaces`, `patches`
(`nx`/`ny`/`vertices`/`grading` rejected there); `geometry.json` `"type": "mesh_defined"` (no
`length`/`height`), required exactly with `multiblock`. `boundaries.json` must configure exactly
the mesh's patch names (`meshPatchNames`). Parser, reader cross-checks, `CaseWriter`
(round trip bitwise) and `CaseBuilder` (→ `createMultiBlock2D`, geometric errors →
`CaseConfigurationError "mesh.json: invalid multiblock mesh: …"`) are in the production path;
documented in `docs/user_guide/case_format.md` ("Multi-block meshes"). The committed cases are
generated by [generate_multiblock_cases.py](generate_multiblock_cases.py) (shared grid lines, so
interface vertices are bitwise identical).

## 4. Single-block / multi-block capabilities

Any number of blocks (≥ 1); a single `multiblock` block is a general body-fitted structured
region (e.g. the 1-block curved channel of G3); blocks may be rotated/mirrored relative to each
other (interfaces between any side kinds, aligned or reversed); a block may be joined to itself
(closed O-grid ring). Existing `structured_cartesian` / graded / `structured_quad` cases are
untouched (§18).

## 6. Internal solid / inactive regions — implemented

Implemented as **holes**: the obstacle is not meshed, eight blocks surround it, and its four
sides form the `obstacle` wall patch (no masks, no hidden cells). Verified: no cell centroid
inside the obstacle, domain area = channel − obstacle to 1e-12, obstacle faces 24 with normals
pointing into the solid, Euler characteristic V − E + F = 0 (one hole) in the unit test, mass
flow 1 through every vertical face line (12 faces where the line cuts the obstacle) to ≤ 1e-6,
mirror symmetry of the solution about y = 0.5 to ≤ 1e-6 (measured ~6e-10).

## 7. Connectivity validation

Solver-independent invariants on two-block, L-shaped, holed, 270° sector and closed-ring meshes
(`test_multiblock_mesh.cpp`): every cell has four faces that list it; cell closure
|Σ ±S_f| ≤ 1e-13 Σ|S_f|; face and boundary counts equal the specification's; area equals the
exact domain area; every boundary face in exactly one patch; `MeshQuality` valid with one
connected region; Euler characteristic 1 − (holes). The two-block rectangle is **the
single-block mesh renumbered**: identical cell geometry (bitwise), identical face centroids /
area vectors / (mapped) owner-neighbour, identical patches. Production: 24 interface faces on
the committed curved channel, all owned by the `first` block.

## 8. Boundary-patch validation

Patches are assembled from the listed sides in order, each side in increasing local index
(unit test: the L-shape `outlet` = upper then lower side; the `step` normal points into the
removed corner); `boundaries.json` must name exactly the mesh patches (missing / extra names are
field-named errors); patch face counts asserted on the production cases (curved channel 12 /
12 / 90 / 90; step 8 / 16 / 112 / 112 / 8; obstacle 24).

## 9. Orientation and ownership

Every internal face's normal points owner → neighbour, every boundary normal outward (all test
meshes); interface faces owned by the `first` block; rotated (90°, 180°) blocks with aligned and
reversed interfaces connect the geometrically adjacent cells (centroid offset exactly across the
interface); declaring the wrong orientation is rejected ("does not coincide").

## 10. Invalid / overlapping geometry detection

Rejected with the offending block/side/vertex/cell named (unit + case tests): no blocks;
duplicate/empty names; wrong vertex count; non-finite vertex; side used twice / in an interface
and a patch / unused; bad block reference; duplicate or empty patch; clockwise or non-convex
cells; interface face-count mismatch; interface vertices off by a gap or by **one ulp**; wrong
orientation; two blocks touching without an interface ("must be joined by an interface");
hanging vertices / non-conformal contact; partial overlap ("cross or touch"); duplicated block
("coincide"); a block entirely inside another (winding number: "covered 2 times"); a corner
touching another block's face interior; a single block wound past 360°. Parser-level errors
name the JSON field (`blocks[1].vertices`, `interfaces[1].orientation`, …).

## 11. Disconnected-domain detection

`MeshQuality` counts connected cell regions (BFS over internal faces); more than one is a
validity failure ("mesh has 2 disconnected cell regions (cells per region: 24, 16); the fluid
domain must be one connected region"), so `CaseBuilder` rejects the case. Covered: separated
blocks and blocks meeting only at one corner.

## 12. Interface conservation

- Structural: an interface is one internal face per pair, so the flux leaving one block is the
  same stored value entering the other (unit test: block balances from the cells' own face lists
  equal boundary + interface fluxes to 1e-12; no boundary face on an interface).
- Mass (G2, production, 3 grids): every radial face line including both interfaces carries the
  inflow to ≤ 8.0e-10; block net flow ≤ 3.1e-10.
- Transparency (G3): the same geometry as one block gives the same solution to
  max |Δu| 4.1e-10, max |Δp| 4.6e-9 of the pressure drop, identical iteration counts.
- Scalar (G5, after the thermal fix): heat through hot end, interface 1, interface 2 and cold
  end agree to ≤ 4.8e-12 Q (§17).

## 17. G5: first failure, root cause, thermal fix, before/after

**First run** ([logs/03](logs/03_production_tests_release_gate_run.log)): G1–G4 passed; G5
failed — heat-flow agreement 1.75e-6 / 2.59e-6 / 3.91e-6 Q (threshold 1e-6 Q) and T-error order
1.80 / **0.147** (threshold 1.5). Work stopped and was reported; the gate was not changed.

**Root cause** ([logs/04](logs/04_gate_failure_diagnostics.log),
[logs/05](logs/05_thermal_fix_instrumentation.log)): in the energy assembly every boundary face
added `A(P,P) += Df`, `rhs += Df·T_b` with `T_b = boundaryValue(T_P^old, d)`. For gradient-type
conditions (Adiabatic, FixedGradient, HeatFlux — all `T_b = T_P + g d`) the solved system
therefore carried a wall flow `Df (T_P^new − T_P^old − g d)` instead of the prescribed
`−Df g d`. The outer loop stopped on `max|ΔT| < 1e-8` and returned a field that had never been
solved with its own boundary values. Instrumented (12 × 30): every linear solve converged
(residual ≤ 1e-10), but the residual of the equation assembled from the returned field decayed
only ×0.985 per outer iteration (1.1 → 1.8e-7 at the "converged" iterate, 841 iterations), and
after iteration 1 `max|ΔT|` equalled the adiabatic boundary-value change exactly. The resulting
wall leak (Df × ΔT_last per face) produced the G5 heat-flow spread, proportional to the outer
tolerance (6.9e-6 Q at 1e-8, 7.0e-8 Q at 1e-10, 7.5e-10 Q at 1e-12); the same iteration error
dominated the tiny T error (order 0.147). With the iteration error removed (tolerance sweep) the
T error converges at order 3.0 — the scheme itself was fine.

**Fix** (production, general — no benchmark special case):

1. `boundaryDiffusionContribution` (`EnergyEquation.hpp/.cpp`), used by both energy-equation
   diffusion assemblies and the conjugate-conduction assembly (`ThermalInterface.cpp`):
   value-prescribing faces unchanged (`A += Df`, `rhs += Df·T_b`, bit-identical); gradient-type
   faces add their exact prescribed flux, `rhs += Df·boundaryValue(0, d) = Df·g·d`, no diagonal
   term (zero for Adiabatic). `storedDiagonalOrZero` keeps a singular all-gradient cell (one-cell
   mesh) a reported status instead of an exception.
2. `runPicardLoop` (`ThermalSolver.cpp`): the stopping rule is unchanged (re-solve, stop on
   `max|ΔT| < tolerance`, which also refines loosely-toleranced solves). With nothing lagging, a
   later outer iteration re-solves an already-solved system whose relative target can be below
   round-off; a BiCGSTAB **Breakdown** there whose residual already meets the linear tolerance
   relative to the first iteration's initial residual is an attained solve (its solution is kept;
   the ΔT criterion decides). Any other non-converged solve, and any in the first outer
   iteration, is still `LinearSolveFailure`.

**Why it is correct:** for a gradient-type condition the discrete boundary flow
`Df (T_P − T_b)` with `T_b = T_P + g d` is `−Df g d` identically — independent of T_P — so the
exact discrete equation has that constant on the right-hand side and nothing on the diagonal; the
pre-fix fixed point satisfied the same equation only in the limit of infinitely many outer
iterations. The fixed-point equation is unchanged (converged answers agree with the old ones to
the old iteration error: ≤ 9.9e-8 K on the committed thermal cases, §18); only the lag is gone.
The breakdown rule accepts only solves whose residual already meets the linear tolerance of the
original problem — i.e. what the first solve had to reach — never a stalled or starved solve.

A first loop change (skip the re-solve once the field met the first solve's linear tolerance)
was rejected: it stopped deliberately loose-tolerance cases after one solve (HeatedCavity
80×80 L2 3.1e-4 vs 1e-6; TwoMaterialConduction 40/80 1.2e-4 / 9.1e-3 vs 5e-6) — recorded in
[logs/05](logs/05_thermal_fix_instrumentation.log).

**Regression tests** (`tests/unit/thermal/test_thermal_boundary_consistency.cpp`, 4 tests):
exact per-type boundary contribution, independent of the owner temperature; after `Converged`
the returned field satisfies its own equation (≤ 1e-9 of the initial imbalance), the insulated
wall carries no heat, every cell balances (≤ 1e-9 of the throughput), the global energy balance
closes (heat in = heat out + prescribed loss, ≤ 1e-9), the heat-flux wall carries exactly q''·A,
≤ 3 outer iterations, answer independent of the outer tolerance (1e-12); the conjugate path
likewise; a singular all-gradient cell reports a status, never throws. Run against the pre-fix
solver (scratch copy with HEAD's thermal sources): 3 of 4 fail exactly on the defect
(consistency residual 1.33e-7 vs 1.02e-8, cell imbalance 7.7e-8, energy imbalance 5.5e-7,
380 / 705 outer iterations). Existing tests updated because they pinned the lagged assembly:
`HeatFluxAndAdiabaticBoundariesMatchHandDerivedRhs` (hand-derived RHS now −q·A, no diagonal),
`NonFiniteTemperatureAtGradientBoundaryThrowsNumericalError` (the NaN now reaches the RHS through
inflow at a gradient face — the only remaining owner-value path), and one comment.

## 21. Failed experiments and limitations

- First gate run failed G5 (§17) — the pre-registered rationale underestimated the lagged-wall
  leak and the exact solution (linear in θ) made the T error iteration-dominated; resolved by the
  solver fix, not by changing the gate.
- The rejected first loop change (§17).
- Test-harness finding: an optimised build's fused `sincos()` differs from Python's `sin` by one
  ulp at some angles; the committed-mesh regeneration check compares within one ulp.
- Two-point wall-shear reconstruction on the curved channel is not monotone / ~first order — not
  used as a gate quantity (probe, [logs/02](logs/02_preliminary_probe.log)).
- The radial-pressure-rise order (1.50 / 1.72) is monotone but not asymptotic on these grids.
- Limitations: conformal interfaces only (no hanging nodes / non-matching blocks); straight
  (chordal) cell edges — curved walls are polygonal; each block a single structured grid; the
  GUI does not edit or draw multi-block meshes and has no multi-block field map (use VTK);
  interface vertices must be bitwise identical (the generator guarantees it; hand-written files
  must share values); the VTK export repeats interface vertices once per block (valid, not
  welded).
- Thermal: the fix covers the energy equation (single-material and conjugate). The same lagged
  gradient-boundary pattern exists in the species transport solver (`SpeciesEquation.cpp`,
  `boundaryConcentrationValue`) and is **not** changed here (outside this fix's scope); inflow
  through a gradient-type temperature face and the explicit non-orthogonal correction still lag
  (converged by the unchanged outer loop).
- Pre-existing, unrelated: `-Wconversion` warnings in `apps/gui/SimulationControllerEditing.cpp`
  (`fieldForMessage`, identical at HEAD); qmllint "unqualified access" warnings of the existing
  QML style (0 errors). ASan / clang-tidy / CI were not run (no commit).
