## 2. The timing churn, proven before it was restored

`results/validation/**` carried 50 modified files. The TODO recorded them as timing-only. That
claim was **re-proved on the tree as it stood**, not taken from the record.

The instrument is the project's own `results/p12-mesh-005/tools/classify_generated_outputs.py`. It
parses `.json` / `.md` / `.csv` structurally and treats only `runtime`, `runtime_seconds`,
`seconds` and the Markdown column `runtime (s)` as timing keys — a bare `wall` or `time` is physics
(`wall_shear_*`, `time_step`) and is always compared.

```text
checked 3028 files;  IDENTICAL 1841,  RUNTIME-ONLY 50,  VALUES 0,  NEW 1137
```

**VALUES 0.** Not one generated output anywhere in the repository — MMS reports, grid-convergence
studies, natural convection, turbulence channels, production cases — differed in a non-timing way.

Only then was `--restore` run. That mode copies back **only** files it classified RUNTIME-ONLY; it
never touches a file classified VALUES or NEW, so a real numerical change cannot be silently
reverted by it. That is why the run was done in two passes: prove first, restore second.

After restoration:

```text
git diff -- results/validation/   0 files
git diff -- cases/ tests/data/    0 files
tracked modified                  67 -> 17
```

**No numerical or reference result was discarded.** The 50 files restored are listed in
`phase2-restore.log`; each differs from HEAD only in a timing field.

## 3. What was deliberately kept out of the commit

### 3.1 Nsight Systems profiler binaries — ~10 MB

```text
results/gpu-disc-001/performance/profiling/gpu-disc-320.nsys-rep   2,904,541 B
results/gpu-disc-001/performance/profiling/gpu-disc-320.sqlite     7,053,312 B
```

Binary databases that cannot be diffed or reviewed and that git would carry forever. They are from
this lineage, so excluding them is squarely inside what the closeout authorises.

**Nothing is lost.** The derived text in the same directory is committed, and the profiler
artefacts turned out to contain nothing anyway:

* `kernel_summary.txt` — *"SKIPPED: … does not contain CUDA kernel data."*
* `api_summary.txt`, `memory_summary.txt` — only an `nsys stats` usage error; the extraction failed.
* `stage_profile_320.log`, `stage_profile_640.log` — the actual per-stage finding, and it comes
  from a **different** tool (`performance/tools/stage_profiler.cpp`), not from nsys.

A `.gitignore` rule was added for `*.nsys-rep`, `*.qdrep`, `*.sqlite`, `*.ncu-rep`, with a comment
saying where the derived text lives. No tracked file anywhere in the repository has any of those
extensions, so the rule hides nothing that was previously kept.

### 3.2 Six zero-byte side-effect files

```text
results/gpu-pipe-001/final-residency/**/*.log.build
```

Compiler-stderr capture files written by the residency harness's `build_run` helper. Zero bytes
means the harness compiled cleanly, which the logs beside them already imply, and the `.log.build`
name sitting next to `.log` is confusing. Deleted as hygiene, not as evidence.

### 3.3 Already ignored, and left alone

Twenty `cmake_test_discovery_*.json` files at the repository root are generated by CTest discovery
and are already covered by `.gitignore`. Confirmed ignored, not committed, not deleted.

### 5.1 Two checks in that script were wrong, and are recorded

Both were false positives produced by my own greps, not findings:

* **debug prints** — the comment filter `^\s*//` was applied to grep's output, which is prefixed
  `file:line:`, so the anchor never matched. A commented-out usage example in
  `include/cfd/core/Exception.hpp` — a file this lineage does not touch at all — read as a stray
  print. Corrected: the comment test now runs against the content after the prefix, and the scope
  is the lineage's own 59 sources.
* **build configuration** — the pattern `-G` matched `Green-Gauss` in a comment in
  `cuda/CMakeLists.txt`. Corrected to real flag spellings, with comment lines excluded.

The corrected script ends with a deliberate failing check that proves its aggregator propagates.

### 5.2 Evidence harnesses use absolute WSL paths

282 scripts under `results/` contain `/mnt/c/Users/Hasib/...`. That is the established convention
for this project's evidence tools — every harness from P12 onward does it, and they are run by hand
on the one workstation that has the GPU. Production code under `src/`, `include/`, `cuda/` and
`apps/` contains **zero** hardcoded paths. Unchanged by this closeout, and already recorded as
technical debt in `TODO.md`.

## 6. The restore had to be done twice, and the second time it refused

Phase 4's qualification re-ran four full test suites, every one of which rewrites
`results/validation/**`. So the churn came back and Phase 5's staging review caught 50 category-E
files staged — which is exactly what that review is for.

The second restore attempt **refused to run**:

```text
checked 3039 files; IDENTICAL 1841, RUNTIME-ONLY 45, VALUES 5, NEW 1148
  STOP: a non-timing difference exists. Not restoring.

VALUES  results/validation/mms/distorted_mesh_mms.json                        (75 differences)
VALUES  results/validation/mms/distorted_mesh_momentum_mms.json               (146)
VALUES  results/validation/mms/distorted_mesh_simple_mms.json                 (102)
VALUES  results/validation/mms/distorted_mesh_simple_mms.md                   (5)
VALUES  results/validation/production/curved_channel_multiblock_grid_convergence.json  (73)
```

The differences are ~3e-9 relative, in distorted-mesh MMS error norms:

```text
/levels[1]/errors/phi_boundary_ring_distorted_corrected/l1
    9.273231616828335e-05  ->  9.27323164706436e-05
```

**Cause, established by experiment rather than argument.** The four tests that write these reports
were re-run under the **Release+CUDA** build alone:

```text
ScalarMMS.DistortedMeshNonOrthogonalCorrection
MomentumMMS.DistortedMesh
SIMPLEMMS.DistortedMesh
MultiBlockProductionCase.CurvedChannelGridConvergence
    4/4 passed, 63.5 s
```

and the classification returned to:

```text
checked 3039 files; IDENTICAL 1841, RUNTIME-ONLY 50, VALUES 0, NEW 1148
```

So the five files had been written last by the **ASan build** (Debug + sanitizers, CUDA OFF), whose
optimization level and FP contraction differ from Release. The reports are sensitive to build
configuration at the 1e-9 level; every one of the four tests passes in both configurations, well
inside its own tolerance. **Nothing about this lineage caused it**, and the values HEAD carries are
Release values, which a Release run reproduces exactly.

**Practical consequence, worth recording:** the generated-output restore has to happen after a
*Release* run, not merely after the last run of any configuration. Restoring after an ASan run
would have committed ASan-flavoured numbers into the Release-flavoured reports.

The script's refusal to restore while VALUES was non-zero is the reason this was caught rather than
quietly committed.
