# METHOD — a library-hash gate is only valid WITHIN one configure state. Mine were not.

```text
found       2026-10-10, when TD-027's GATE_A3 freeze aborted on a library-hash gate
affects     every harness in this campaign that gates on `libcfdcore.a == 852555cf…`
status      a defect in MY HARNESS DESIGN, not in the code. The code's behaviour is deliberate
            and documented (P13-004). No production change is warranted.
```

---

## 1. What happened

TD-027's GATE_A3 freeze script asserted

```bash
[ "$LIB" = "852555cfda54f8da013bde93f9c205c15daf2e5291d7920a3744b86e9853c7f8" ]
```

and aborted. The source was unchanged (`fa815c97…`), nothing had been edited, and three consecutive
rebuilds gave a stable `1c4d8502…`. So the build is still bit-reproducible — the *identity* moved.

## 2. The cause, which is a feature

`build/release/generated/include/cfd/core/Version.hpp`, generated by CMake at configure time:

```cpp
// P13-004: which build produced a result. "unknown" when the tree has no
// git (an exported tarball), and "<sha>-modified" when the working tree
// had uncommitted changes -- an honest answer beats a commit the binary
// does not actually match. Fixed per configure, so it never makes two runs
// of one binary differ.
inline constexpr std::string_view kBuildIdentity = "4b37d1107dee-modified";
```

`libcfdcore.a` links `Version.cpp`, so **the archive embeds the commit SHA**. Reconfiguring after a
commit changes `kBuildIdentity`, which changes the archive's bytes.

Note the recorded identity is `4b37d110`, not the current `HEAD` of `0a9bc42`: it is fixed *per
configure*, not per build. So the archive's hash tracks **the commit at the last configure**, which
is a third thing, distinct from both the source and `HEAD`.

## 3. Why this invalidated a gate I used all day

Every harness today carried a check of the form "the library must hash to `852555cf`". That value
was recorded when `build/release` was last configured at an earlier commit. **Eight commits later it
is unreachable**, and the gate fires on every run — correctly, and for a reason that is not a defect.

```text
WHAT THE GATE WAS TRYING TO ASSERT   "the code under test is the code I think it is"
WHAT IT ACTUALLY ASSERTED            "the code under test, AND the commit at last configure, are
                                      what they were when I wrote this number down"
```

The second is strictly stronger and is not what any of those harnesses needed.

## 4. The corrected design

```text
GATE ON       the SOURCE hash. `src/species/PremixedFlame.cpp == fa815c97…` is the stable identity
              of the code under test and is unaffected by commits, configures or build identity.
RECORD        the library hash, always -- it is the provenance of the artefact that ran.
COMPARE       library hashes only WITHIN a run: "the two legs must differ" (a two-library
              attribution) or "this leg must equal the leg built five minutes ago". Never against a
              value recorded before a commit.
ALSO GATE     binary-newer-than-source, which CLAUDE.md §8 requires and which is orthogonal to all
              of the above.
```

## 5. What is and is NOT invalidated by this

```text
NOT invalidated   the A3 and A6 verifications, or TD-040's dt ladder, or any run that PASSED its
                  gate. At the moment each ran, the configure state matched and the recorded
                  library hash was the artefact that executed. Those records are accurate for
                  their moment.
NOT invalidated   the two-library attributions. They compared two libraries built minutes apart in
                  one configure state, which is exactly the valid use.
NOT invalidated   any physics result. No measurement changes.
INVALIDATED       the REUSABILITY of those hashes as gates in later runs. A harness re-run after a
                  commit will abort, and the abort means "the build identity moved", not "the code
                  changed".
A GAP             the freeze logs for TD-004's GATE_A3 and GATE_A6 record "library under test:
                  852555cf…" without noting that the value is configure-state-dependent. The
                  frozen GATE files themselves are unaffected -- they gate on criteria, not on
                  library hashes.
```

## 6. The lesson

```text
A hash gate must be anchored to something that changes ONLY when the thing it protects changes.
`libcfdcore.a` changes when the COMMIT changes, so it cannot anchor a claim about SOURCE.
```

This is the tenth instrument or method defect in this campaign, and the second today whose cause was
a correct, documented feature of the code being mistaken for a stable invariant — the first being
the fuel balance's instantaneous-vs-cumulative accounting in TD-040 §2.1.
